# WSL secret store for t3code: gnome-keyring with blank-password default keyring

t3code needs a Secret Service provider on the WSL guests (`harpe`, `warpe`); without one it cannot persist credentials. Both guests therefore get `services.gnome.gnome-keyring` plus seahorse through `modules/system/config/secret.nix`, imported by the shared `modules/system/config/wsl/`. PAM auto-unlock cannot work on this path — WSL session creation performs no password auth (passwordless `nullok` account), so there is no login password for `pam_gnome_keyring` to unwrap the keyring with, and all its PAM lines are `optional` by design. Instead, the Default keyring's password is set blank once via seahorse; the daemon dbus-activates on demand and opens blank-password keyrings without prompting, so t3code launches and connects (warpe to the pewter remote workspace) with no interaction. At-rest secrecy is delegated to the Windows disk (BitLocker): a blank keyring password adds no meaningful exposure on an encrypted WSL vhdx, and the keyring holds only agent session tokens, never the fleet age identity. Verified by restarting WSL and launching t3code on warpe with no prompts, connected to pewter.

Considered and rejected: a real-password keyring with manual unlock each boot (daily friction with no headless unlock path that doesn't store the password elsewhere anyway), a sops-managed password piped to `gnome-keyring-daemon --unlock` from a user unit (a second secret to rotate guarding the same tokens; revisit if the keyring ever holds anything sops-worthy), and no Secret Service at all (t3code loses credential persistence).

Status: accepted

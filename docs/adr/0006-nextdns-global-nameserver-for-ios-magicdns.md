# NextDNS as tailnet global nameserver for iOS MagicDNS resolution

Pairing the t3code remote workspace from the phone failed: the iOS browser (Firefox, iOS 26.6, Tailscale app 1.102.2) reported "the specified hostname could not be found" for the pairing URL `https://pewter.tail3f9fd2.ts.net/`, while gram paired fine with the same URL. The tailnet's ts.net hostnames exist only inside MagicDNS — public resolvers (the phone's NextDNS) answer NXDOMAIN for them — and iOS, unlike gram's systemd-resolved (which splits `*.ts.net` to 100.100.100.100 and everything else to NextDNS via `~.` in `resolved.nix`), fell back to its own resolver for all queries because the tailnet had no global nameserver configured. Adding NextDNS as the tailnet's Global Nameservers in the admin console (with "Use with exit node" and "Override local DNS" enabled, matching gram's all-to-NextDNS behavior) activates the tunnel's split-DNS on iOS: ts.net names resolve via MagicDNS, everything else goes to NextDNS. No iOS app toggle was involved — no "override system DNS" setting exists in the current iOS app; the admin-console nameserver is the mechanism. Consequence: LAN hostnames like `router.local` no longer resolve on tailnet clients (NextDNS can't answer them), and any device-local NextDNS DoH profile would still shadow the tunnel DNS, so none is installed on the phone.

Prevention rule: any tailnet-exposed HTTPS service reachable from iOS requires the tailnet to have at least one global nameserver configured — MagicDNS alone does not push the split resolver to iOS clients.

Considered and rejected: a NextDNS Rewrite mapping `pewter.tail3f9fd2.ts.net` → `100.118.121.100` (works but manual per-hostname and brittle), and per-device DNS configuration on the phone (fragile, diverges from the declarative tailnet config).
